Welcome to the Ramos Book

Ramos is a small, self-hosted language that compiles directly to native Linux x64 and Windows x64 executables. Its two guiding rules are simple programming and measured speed.

This book describes Ramos 0.18.0. Markdown chapters are the canonical edition for AI agents, review and offline reading. The HTML edition is generated from those same chapters for comfortable human reading. Historical version labels identify when a feature arrived; they do not change this book's baseline.

What you can use today

Checked int64 and finite float64 arithmetic, booleans, functions, comments, while/range loops, else-if chains, compound assignment, immutable UTF-8 strings, mutable bytes, structs, typed arrays, reclaiming managed memory, compile-time weave, stdin, streamed files, terminal interfaces and Windows native GUI controls, directory iteration/creation, lexical path helpers, environment lookup, direct child execution and reusable UTF-8 text builders. Text builders provide immutable snapshots and capacity reuse/release for streamed tools.

Native math adds explicit conversions, square root and fixed decimal formatting. There are no namespaces, networking APIs or package registry in 0.18. Read the OS libraries for directory and child-process contracts. See the new syntax for ranges, else-if chains and compound assignment. See the limits and proposed roadmap. Planned syntax must not be used in programs targeting this version.

Use ramos run app.ramos to compile and execute a source file directly, or build to save an executable. ramos fmt formats a copy or checks formatting. Authoring tools explain arguments, errors and cleanup.

Install, build and run

Use the complete 0.18.0 math bundle, which also includes the CLI/TUI tools, both compilers, examples and all thirteen libraries. Extract the archive and keep its directory structure. The published SHA256SUMS.txt file lists asset hashes for integrity checking.

Your first source file

Save hello.ramos as UTF-8 in the extracted directory:

fn main() {
    print(s"Hello, Ramos!")
}

Windows x64 — PowerShell

.\ramos.exe --version
.\ramos.exe run .\hello.ramos
.\ramos.exe build .\hello.ramos -o .\hello.exe
.\hello.exe

Expected output: Hello, Ramos!. Python, a C compiler and a separate runtime are not required to compile or run programs with the downloaded compiler.

./ramos-linux-x86_64 build hello.ramos -o hello
./hello

Rebuilding an existing output

Use --force only when you intend to replace an existing executable:

./ramos-linux-x86_64 build hello.ramos -o hello --force

A failed compilation preserves existing output. The compiler refuses source file aliases as output even with --force.

Diagnostics, formatting and running source files

The compiler, formatter and compile-and-run driver are written in Ramos. The native OS boundary only publishes a temporary executable, runs it and cleans up. No interpreter, shell, Python, C compiler or separate backend is needed.

Run a source file

Linux:

./ramos run examples/hello.ramos
./ramos run examples/rgrep.ramos -- needle README.md

Windows PowerShell:

.\ramos.exe run .\examples\hello.ramos
.\ramos.exe run .\examples\rgrep.ramos -- needle README.md

run SOURCE.ramos [-- ARG...] compiles for the OS running the compiler, using the same checks, source-relative weave loading and machine-code generation as build. Program arguments follow an explicit --; empty arguments, spaces, Unicode, quotes and shell metacharacters remain individual values. No shell or PATH lookup is involved. Stdin, stdout, stderr, environment and working directory are inherited. The compiler prints nothing on success beyond the program's output.

Use build for distributable executables, cross-compilation or --gui output; run accepts none of those build options and creates no output in your project. It waits for the program and forwards exit statuses 0..255. Larger Windows exit codes map to 1; Linux signal termination is represented as 128 plus the signal number. Compiler, launch or cleanup failures return 1 with an error. arg(0) is the temporary executable path on Linux and ramos-run on Windows; user argument values start at arg(1) on both platforms.

The argument limit is 256 user values and 32767 packed UTF-8 bytes. Linux counts NUL separators; Windows counts the quoted command line including its placeholder argument zero. Embedded NUL is rejected. All existing source, code, memory and call-depth limits remain enforced.

Temporary executable lifetime

Compilation finishes before any temporary executable is created. Linux uses nonempty TMPDIR, otherwise /tmp; Windows uses GetTempPathW (TMP, TEMP, USERPROFILE, then the Windows directory). The base must exist and permit directory creation and executable launch. Each run exclusively creates its own ramos-run-… directory; an existing candidate is never reused. Linux permissions are 0700. Windows directory permissions follow the base directory's security settings. A bounded 16 attempts avoids an unbounded collision loop.

The driver atomically publishes app.exe inside this directory, launches it directly, waits, deletes the executable and removes the empty directory. The same cleanup runs after launch/write failures and handled child runtime errors. Cleanup errors are reported. It never recursively deletes child-created files. Abrupt compiler termination or a machine crash can leave temporary files; crash durability and cleanup after forced termination are not promised.

Format a file

./ramos fmt app.ramos
./ramos fmt app.ramos --check
./ramos fmt app.ramos -o formatted.ramos
./ramos fmt app.ramos -o formatted.ramos --force

Use .\ramos.exe for the same commands in PowerShell. The default writes exact formatted UTF-8 bytes to stdout. --check writes nothing and returns 0 for an unchanged file, or reports needs formatting: FILE and returns 1 for a change. Read, lexical or output errors also return 1.

-o writes a new non-executable file atomically. An existing destination requires --force. Source identities, hardlink aliases and symlink aliases are protected even with --force; failed formatting preserves an existing destination. There is no in-place mode. Avoid redirecting stdout back to the source, because a shell can truncate it before the compiler reads it. Prefer -o for a new copy.

The first formatter normalizes horizontal spacing and uses four spaces per brace level, plus one continuation level inside multiline parentheses/brackets. It preserves token spelling, string literal bytes, comment content (including comment trailing spaces), and existing LF/CRLF line breaks. One-line bodies remain one line. Nonempty input receives a final newline if missing, using the first existing line-ending style or LF. Empty input stays empty. Formatting is idempotent.

It formats one source file without loading woven files and does not require a main function. UTF-8, escapes, comment termination, NUL and token bounds are checked; full grammar and types are checked by build or run. The input and formatted output limits are each 1 MiB; expansion beyond the output limit fails before publication. Statement-separating newlines inside block comments are retained. Separate operator tokens in unfinished code stay separate.

Read a compiler error

app.ramos:2:12: error: expected bool, found int64
  |     if 123 { print(1) }
  |            ^

Errors retain the original woven filename, line and byte column, then show the relevant source line and a caret. Type messages name arrays and declared structs, for example expected [int64], found [string] or expected Point, found Player. The caret identifies the compiler's failing token/location; it is not necessarily the start of the expression causing a type error.

Tabs display as four spaces. Non-ASCII and control bytes display as \xNN so terminal controls cannot execute and caret alignment is deterministic; Unicode text is byte-escaped in this first preview. Long lines show at most 80 source bytes on either side of the location, with ellipses for omitted text. Columns remain byte-based rather than terminal display-cell positions.

The language

Syntax

fn main() {
    let price = 20
    var count = 3
    print(price * count)

    count = count + 2
    print("Updated total:")
    print(price * count)
}
  • Exactly one parameterless main returning void is required. Other top-level functions and structs may appear before or after it. weave adds library definitions at top level.
  • print accepts a string literal, buffer, integer, float64 or boolean expression and adds a newline. Booleans print as true or false; floats use six fractional digits.
  • Integer expressions support +, -, *, /, %, unary +/-, and parentheses. Multiplication, division, and remainder bind more tightly than addition and subtraction. Binary operators at the same precedence associate left to right.
  • Integers range from -9223372036854775808 to 9223372036854775807. -9223372036854775808 is accepted as a directly negated literal; its positive magnitude cannot be used as an ordinary positive literal.
  • let declares an immutable binding; var declares a mutable binding. Every binding must have an initializer. int64, float64, bool, bytes, string, struct and array types are inferred and fixed for the lifetime of the binding.
  • Binding reassignment is supported only for var; fields and array elements can be mutated through let. Names must be declared before use; duplicate declarations in the same block are errors. Inner blocks may shadow outer names, and their bindings are invisible after the block ends. Identifiers use ASCII letters, underscores, and digits, with a letter or underscore first. Keywords are reserved. "..." produces bytes; s"..." produces immutable UTF-8 strings.
  • Separate statements with newlines; the final statement may directly precede }. Newlines after operators and opening parentheses are allowed. Semicolons are not implemented. Comments use // or non-nesting /* ... */; newlines in block comments retain their statement-separator meaning.
  • Input is UTF-8. String escapes are \n, \t, \r, \", \\, and \0.
  • Empty bodies, empty strings, LF, and CRLF are supported.
  • Raw NUL source bytes, malformed UTF-8, unsupported escapes, and raw newlines inside strings are rejected. Diagnostics contain filename, line, and byte column.

Booleans and control flow

fn main() {
    var running = true
    var count = 0
    while running {
        count = count + 1
        if count == 5 {
            running = false
        } else {
            print(count)
        }
    }
    print(!running)
}
  • true and false are distinct boolean literals; ! negates a boolean.
  • <, <=, >, and >= compare two signed integers or two floats. == and != compare two integers, two floats, two booleans or two strings. Mixing types is a compile-time error.
  • && and || require booleans and short-circuit left to right; skipped operands still undergo type checking.
  • From lowest to highest precedence: ||, &&, equality, ordering, addition/subtraction, multiplication/division/remainder, unary signs/!, and primary expressions. Operators at one level associate left to right. 1 < 2 < 3 is rejected; combine pairwise comparisons with &&. Arithmetic requires matching numeric types; + also concatenates strings.
  • if condition { ... } else { ... } and while condition { ... } require a boolean condition. else is optional and may follow on a new line. Branches use braces; else if chains test later conditions only when prior arms fail.
  • while reevaluates its condition before every iteration. break exits the innermost loop; continue reevaluates its condition. Both require a loop. while true runs until a break or a runtime failure; there is no implicit iteration limit. Code in skipped branches is type-checked but not executed.
  • Bindings initialize whenever execution reaches their declaration. A shadowing initializer can refer to the outer binding. Blocks do not expose their locals.
  • for name in start..end { ... } evaluates int64 bounds once, then counts upward with an excluded end. The counter is immutable and local to the body; empty/reversed ranges do not run. break/continue target the innermost loop.
  • += accepts int64/float64/string, -= accepts int64/float64, and both are statements with matching operand types. Destinations and indices evaluate once, before the RHS. Bindings require var; fields/elements retain mutation through let. Separate statements with newlines, including after a compound statement.

Run make control-flow for a native Fibonacci/loop example.

Functions

fn factorial(n: int64) -> int64 {
    if n == 0 {
        return 1
    } else {
        return n * factorial(n - 1)
    }
}

fn main() {
    print(factorial(10))
    announce()
}

fn announce() {
    print("Functions work!")
}

Parameters require non-void type annotations and their bindings are immutable. Results can declare any value type or void; omitting the result means void. Calls evaluate arguments left to right and require exactly matching types and argument counts. Functions may call later definitions, themselves or each other. A lexical binding can shadow a function name; that name then cannot be called. main is the process entry and cannot be called by user code.

return expression must match the declared value type; bare return is for void functions, including main. A value function must return on every statically checked path. Both arms of an if/else may establish that guarantee. Loops are checked conservatively, so even a while true needs a return after it for a value function. Unreachable statements are still type-checked. Void calls may be statements; value calls used as statements discard their result.

Every call has its own local frame. At most 64 Ramos calls may be active, including main; attempting the next call reports a runtime error and exits 1. Normal returns release the frame and restore the active-call counter. This check assumes an ordinary Linux process stack; it cannot compensate for an unusually small stack limit selected by the caller.

Run make functions for factorial, a digit classifier and a void helper. See the native calling convention for compiler details.

Arithmetic behavior

The overflow rules below apply to int64. Float64 uses a finite-value policy, explicit conversions and gradual underflow.

Generated native instructions check signed overflow for addition, subtraction, multiplication, and negation. Division truncates toward zero; a remainder has the dividend's sign. Division or remainder by zero, and either operation on INT64_MIN with divisor -1, fail explicitly.

A failed arithmetic operation writes a runtime diagnostic to stderr and exits with status 1. It never silently wraps or depends on an unhandled CPU divide fault. Successfully completed programs exit with status 0. Earlier output is retained if a later operation fails.

Easier syntax: branches, ranges and assignment

Ramos 0.14 adds else if, ascending exclusive-range for, and the statement operators += and -=. It keeps checked arithmetic, native Linux/Windows output and the self-hosted Ramos compiler. These are syntax conveniences over the existing branch, loop and expression emitter, not an interpreter or backend.

fn describe(n: int64) -> string {
    if n < 0 { return s"negative" }
    else if n == 0 { return s"zero" }
    else { return s"positive" }
}
fn main() {
    var total = 0
    for i in -2..4 {
        if i == 0 { continue }
        total += i
    }
    print(total)                  // 3
    print(describe(total))        // positive
    var message = s"Hello"
    message += s", Ramos!"
    print(message)
}

Else-if chains

Write if condition { ... } else if condition { ... } else { ... }. Conditions must be booleans. Only the first matching arm runs, and later conditions are not evaluated after a match. All arms remain type-checked. Newlines/comments can separate a closing brace, else and if.

Each arm has its own lexical block. A chain guarantees a value-function return only when it has a final else and every arm guarantees return. A chain without that final fallback does not prove that every input is covered. Chaining does not consume another block-stack level for each arm; genuinely nested bodies still obey the existing nesting limit.

Ascending, end-exclusive ranges

for name in start..end { ... } evaluates start and then end, once each, including when the range is empty. Both are int64 expressions. The counter takes start, start + 1, and so on while strictly less than end. A range with start >= end is empty, not descending. Parentheses, negative bounds, calls, multiline expressions and comments are allowed.

The counter is an immutable int64 binding scoped to the loop body. It can shadow an outer name, but the bounds still see that outer binding: the counter does not exist until both bounds have been evaluated. A declaration in the same body cannot redeclare it; a genuinely nested block may shadow it. No counter binding leaks after the loop. Each iteration initializes body locals anew.

break exits the innermost for or while; continue goes to the next range value or reevaluates a while condition. Body locals are cleared on either path. Loop return analysis stays conservative: a loop by itself does not guarantee a value-function return. There are no step/descending/inclusive-range variants.

The increment retains an overflow check. With an immutable counter and a signed end-exclusive bound it cannot need to advance beyond INT64_MAX: 9223372036854775806..9223372036854775807 runs once and finishes normally.

Each range reserves one source counter and one hidden bound slot. Both count against the checked 4096-declaration budget; frame storage and cleared scope slots remain part of the existing memory model. Active-call depth stays at 64; this release does not raise it without a reviewed stack budget.

Compound assignment

Statement Allowed destination/result
destination += expression int64 addition or string concatenation
destination -= expression int64 subtraction

The operand types must match exactly. These are statements, not expressions; print(n += 1) is invalid. ++, *=, /= and wrapping arithmetic are not added. Bytes and typed arrays do not acquire concatenation or arithmetic.

An ordinary destination binding must be var. A struct field or typed-array element can be mutated through let, following the existing aliasing model:

struct Item { count: int64, name: string }
fn main() {
    let item = Item(2, s"Ramos")
    item.count += 3
    item.name += s" book"
    let values = array(int64, 1, 9)
    values[0] -= item.count
    print(values[0])             // 4
}

Evaluate the destination reference and every index once, then read its current value, then evaluate the right-hand expression and write the combined result to that same destination. Bounds failure occurs before right-hand side effects. A right-hand call that replaces an aggregate reference does not redirect the pending write. The original aggregate/value stays rooted across allocations and collection. String addition allocates a new immutable value; it is not an amortized string-builder operation.

Overflow reports the ordinary arithmetic runtime error and exits 1. String limits, UTF-8 validation, array bounds and heap limits are unchanged.

Native float64 and essential math

Ramos adds a float64 value type on Linux x64 and Windows x64. Arithmetic emits SSE2 instructions directly; decimal literal conversion is implemented in the Ramos-written compiler. Python is only an independent test reference, not part of compilation or execution. Integer arithmetic remains checked int64.

A complete program

weave "stdlib/math.ramos"
struct Point { x: float64, y: float64 }
fn main() {
    let p = Point(1.25, 2.5)
    let samples = array(float64, 2, 0.0)
    samples[0] = p.x
    samples[1] = p.y
    p.x += 0.5
    print(p.x)
    print(math_text(math_sqrt(2.0), 3))
    print(float_to_int(-2.9))
    print(samples[0] < samples[1])
}

Output: 1.750000, 1.414, -2, true, each on its own line. Keep stdlib/ beside this source, then use ramos run app.ramos or build a saved executable.

Literals and types

1.25, 1.0, 1e2, 1.25e+2 and 1E-3 are float literals. A decimal point requires digits on both sides: use 0.5, not .5, and 1.0, not 1.. An exponent requires digits after its optional sign. A sign is a unary operator. Integer literals and the integer range syntax 0..n keep their existing meaning.

Each literal admits at most 768 mantissa digits (including leading zeros) and a written decimal exponent from -400 through 400. The exponent limit applies before adjusting for fractional digits. Exact integer-rational conversion rounds once to the nearest binary64 value, breaking halfway ties toward an even significand. Literals rounding outside the finite range are compile errors; tiny literals may round to a subnormal value or zero. -0.0 retains its sign.

Bindings infer float64; function parameters/results, struct fields and nested array types can explicitly use float64. Array elements occupy eight bytes. Calls and assignment require matching types. float64 is a new reserved keyword; float_to_int, float_to_text and float_sqrt are reserved intrinsic names. Older programs defining these names need renaming.

Two floats support +, -, *, /, unary signs, all six comparisons and +=/-=. They follow the existing integer operator precedence. % is unsupported. Mixed int/float operations are compile errors: write float64(n) + 0.5. Booleans require explicit comparisons; floats cannot be range bounds or indices. + does not implicitly format numbers or concatenate floats with strings.

Finite arithmetic and errors

The representation is binary64: a sign, eleven exponent bits and 52 stored fraction bits. See the primary representation reference. Ramos uses round-to-nearest/ties-to-even SSE2 arithmetic, with gradual underflow and no fused multiply-add contraction. Decimal fractions such as 0.1 usually have an approximation in this representation; exact equality compares the stored numerical values. Positive and negative zero compare equal.

Ramos deliberately exposes finite values only. An operation producing infinity or NaN, division by either signed zero, square root of a negative nonzero value, an invalid conversion or a formatting precision outside 0..18 writes a Ramos runtime error and exits 1. Previous output remains. There is no full IEEE-754 conformance claim, exposed NaN/infinity, exception flag API or rounding-mode API. Underflow rounding to a subnormal or signed zero is allowed. Square root of negative zero preserves negative zero. Integer overflow and bounds traps remain.

Explicit conversions and printing

Intrinsic Contract
float64(value: int64) -> float64 Round an integer to nearest/ties-to-even binary64; integers larger than 2^53 in magnitude may lose precision
float_to_int(value: float64) -> int64 Truncate toward zero; input must be in [-2^63, 2^63), otherwise trap
float_to_text(value: float64, places: int64) -> bytes Fresh decimal bytes with exactly 0..18 fractional digits, nearest/ties-to-even decimal rounding
float_sqrt(value: float64) -> float64 Hardware square root with checked domain and finite result
print(value: float64) Fixed decimal with six fractional digits and LF

float_to_int(-2.9) returns -2. float64(9223372036854775807) rounds to 2^63, so converting that result back traps. The included lower bound -2^63 converts successfully. There are no implicit conversions.

Formatting rounds the exact stored binary value using integer arithmetic; it does not round an approximate decimal multiplication. Thus float_to_text(0.1 + 0.2, 18) produces 0.300000000000000044. float_to_text(2.5, 0) produces 2; float_to_text(3.5, 0) produces 4. Negative zero formats with -. Very large values use full fixed decimal notation. Wrap with string(...) for UTF-8 string operations, or use math_text.

Fixed printing is not a shortest-decimal, scientific or lossless round-trip format. Tiny values may print as zero at the chosen precision. Text-to-float parsing, trig/log/power functions and arbitrary precision are not provided yet.

Ramos math library

Weave stdlib/math.ramos. Its helpers use ordinary Ramos code:

  • math_abs(value) normalizes either zero to positive zero.
  • math_min(a, b) and math_max(a, b) return the first argument on equal values, including signed-zero ties.
  • math_clamp(value, low, high) rejects reversed bounds with a library error/exit 1.
  • math_sqrt(value) wraps the checked intrinsic.
  • math_text(value, places) returns an immutable string with fixed decimal digits.

All numerical arguments above are float64; formatting precision is int64. There are thirteen bundled libraries in 0.18.

Strings, structs, arrays and memory

These features implement the first three priorities from the developer feedback. Both native targets use the same checked semantics. Existing byte-buffer programs keep their byte-literal and API behavior; discarded allocations can now be reclaimed. string/struct are new keywords and the new intrinsic names are reserved for function definitions. Older programs defining those names must rename them. The compiler's old string helper was renamed string_literal for this reason. The compiler remains written in Ramos and emits ELF/PE directly.

Immutable UTF-8 strings

fn join(a: string, b: string) -> string { return a + b }
fn main() {
    let greeting = join(s"Hello, ", s"🌍")
    print(greeting)
    print(len(greeting))              // 8 Unicode scalars

Structs

struct Point { x: int64, y: int64 }

Fields require non-void types. Definitions may be referenced before they appear, including from function signatures or other structs. Fields are separated by commas or newlines. Duplicate names, missing types and unknown fields are compile errors.

Structs are mutable boxed values. Assignment, parameters and returns copy a handle, so aliases observe field writes. let protects the binding while allowing field changes, as it already does for bytes. The checked limits are 64 struct types and 16 fields per type.

Reusable memory

Bytes, strings, structs and arrays use a nonmoving conservative mark/sweep heap. When allocation cannot find space, it collects unreachable objects and retries. collect() requests collection explicitly; memory_used() reports currently allocated block bytes, including headers/padding and not-yet-collected garbage. A reachable returned value, argument, active expression or aggregate field remains valid. Unreachable cycles can be reclaimed. Every reused payload is zeroed. Scope exit, break and continue clear ended local slots.

The heap holds at most 16 MiB of allocated blocks, plus an 8 MiB ownership map. Each block needs a 32-byte header and alignment to eight bytes. Empty values therefore consume 32 bytes. Mapped memory is RW and never executable. Stdin retains its separate lazy 1 MiB + 12 KiB scratch mapping.

The collector scans active stack words/saved registers and object payload words. An integer, float payload or byte sequence resembling an allocated address can retain that object conservatively. This is not an exact memory-accounting or real-time GC guarantee. There is no manual free, pointer cast, moving collection or dangling alias API. A program whose reachable data exceeds the heap still traps; the change removes the cumulative-allocation limit, not the bounded live heap.

fn main() {

Bytes versus strings

These typed native intrinsics work in Linux ELF and Windows PE programs. They use the existing bytes, int64 and bool types; no new syntax or dependencies.

Decimal conversion

int_to_text supports the entire signed 64-bit range, including -9223372036854775808. Zero becomes "0". It adds neither a terminator nor a newline and leaves parse_error and io_error unchanged.

text_to_int accepts ASCII [+-]?[0-9]+, including leading zeroes. It rejects empty input, a sign without digits, whitespace, NUL, non-ASCII digits, prefixes, decimal points and trailing bytes. Check parse_error() immediately afterward:

  • 0: success, including a valid zero.
  • -22: invalid decimal syntax.
  • -34: valid decimal syntax outside the signed 64-bit range.

Invalid syntax takes precedence over overflow: "999999999999999999999x" reports -22. Every byte is validated even after overflow. Parsing does not allocate and has no digit limit beyond the existing 1 MiB buffer limit. parse_error is independent of I/O status and changes only on text_to_int.

Line input and EOF

read_line blocks until LF, EOF or a read failure. An empty line is a successful empty buffer with io_error() == 0 and stdin_eof() == false. A final line without LF is returned in full and sets EOF true. Subsequent reads return empty bytes with status zero. Process a nonempty final line even when EOF is already true:

fn main() {
    var done = false
    while !done {
        let line = read_line()
        if io_error() != 0 {
            stderr("cannot read stdin\n")
            exit(1)
        }
        if buffer_len(line) == 0 && stdin_eof() {
            done = true
        } else {
            print(line)
        }
    }
}

LF and exactly one CR immediately before LF are removed. A bare CR at EOF is retained. Other bytes, including NUL and invalid UTF-8, are preserved.

Payloads up to 1 MiB excluding LF/CRLF succeed. An oversized line is drained to its next LF or EOF, then returns empty bytes with io_error() == -27. The next line remains available. OS failures return empty bytes and a negative I/O status; a consumed partial line is discarded. Failures do not themselves mark EOF. Every read_line updates io_error, including resetting it after successful reads or EOF; it does not change decimal parse status or file identity protection.

Input is read in 4 KiB chunks. A private lazy RW scratch mapping of 1 MiB + 12 KiB is reused outside the 16 MiB value heap. Returned lines are fresh mutable heap allocations sized to their payload, so short lines do not each consume 1 MiB. Version 0.10 can reclaim discarded lines; allocation still traps if live data exceeds the heap. Do not mix this buffered API with another consumer of stdin.

Linux reads fd 0 directly and retries EINTR. Windows uses GetStdHandle and ReadFile; broken pipe and handle EOF are treated as normal end of input. Redirected files and pipes retain raw bytes. Windows console input follows its configured input code page, unlike the UTF-8 command-line argument API; Ramos does not promise UTF-8 console input. See Microsoft's ReadFile contract.

Libraries with weave

Ramos uses weave to add a library at compile time. The name was chosen by the project owner instead of the conventional import keyword.

}

A library is an ordinary UTF-8 .ramos source file containing functions, structs and optional further weave statements. Call its functions normally. There is no package manager, runtime module loader or separate library backend. Resolution and names

Paths are relative to the file containing the weave, including inside another library. They do not depend on the shell's current directory. Use / separators on Linux and Windows. Spaces and UTF-8 names are supported. Paths must be nonempty and relative; absolute/drive-relative paths, control characters and backslashes in directives are rejected. . and .. are normalized lexically. The root CLI source can still use a normal absolute or relative host path.

Each normalized source path loads once, so repeated and shared dependencies are allowed. ASCII case is folded for path comparison on Windows. Symlink paths are not resolved to a universal canonical name; distinct alias paths can still produce duplicate-definition errors. File identities are separately protected against output overwrites.

Use one weave "path.ramos" per statement, terminated by newline or EOF. It must occur at top level. Comments can surround it; directive-like text inside comments/literals is ignored. Dependency cycles are compile errors with a source location. Libraries cannot define main; the root executable defines it.

Definitions share one namespace. Functions/types may refer forward across files, but duplicate names are errors. Prefix reusable library functions, as the standard library does with num_, text_, bytes_, list_ and map_. Namespaces, aliases, selective exports and package registries are not part of this small first library system. weave is a new reserved keyword; older user functions/bindings using that name need renaming.

Diagnostics identify the original file, line and byte column, including lexer and type errors inside libraries. A missing file reports the containing weave site and requested path. Failed builds preserve existing output. With --force, the compiler still refuses to replace any source identity it loaded, including a source's hardlink/symlink alias.

dir_kind(handle: int64) -> int64 Kind of latest returned entry, zero without an entry
dir_close(handle: int64) -> int64 Zero success or negative error; retires a valid ID even on close failure
dir_create(path: bytes) -> int64 Zero success or negative error

All overwrite io_error() with zero on success or a negative status on error. Capture it before another I/O operation. Directory IDs use the same increasing generation counter as file streams, with separate lookup tables: file and directory handles cannot be substituted. Closed IDs remain invalid after slot reuse. There are 64 concurrently open directories, separately from 64 file streams. Limit exhaustion is fallible (-24); invalid handles return -9.

Paths must be nonempty, NUL-free and at most 4095 input bytes. Windows validates UTF-8 and uses wide APIs; Linux preserves arbitrary filename bytes. Host Windows path-length and filesystem restrictions still apply; this release does not add an extended-path prefix or a long-path opt-in manifest. A caller-supplied root path may follow a link. Entries themselves are classified without following links. Linux resolves unknown entry kinds with fstatat(..., AT_SYMLINK_NOFOLLOW). Missing paths return -2, non-directories -20, access denied -13; other native Linux errno values are preserved. Windows maps unclassified failures to -5.

Path helpers and environment

stdlib/path.ramos provides path_join(parent: string, child: string) -> string, path_name(path: string) -> string, path_absolute(path: string) -> bool, and byte-preserving counterparts path_join_bytes, path_name_bytes, path_absolute_bytes. These helpers are lexical: no filesystem access or .. normalization. A rooted child replaces its parent; joining an empty child returns the parent. Linux recognizes /; Windows also recognizes \ and C:/.... Windows rooted paths such as /x are drive-rooted, and C:file stays drive-relative: path_absolute means rooted, not a canonical full path. path_name strips trailing separators and returns the last component; a root made only of separators has an empty name. Generic helpers retain the ordinary 1 MiB value limit; native OS calls enforce their narrower path limits.

stdlib/system.ramos provides system_cwd() -> SystemValue and system_env(name: string) -> SystemValue, with value: bytes and status: int64. Missing environment names return -2; an existing empty value has status zero. Empty names, embedded NUL and = are invalid (-22). Values are limited to 32767 bytes (-27 when exceeded); Linux names over 32767 bytes are invalid, Windows oversized UTF-8 name input returns -27. Lookup follows native OS case rules (case-sensitive Linux, case-insensitive Windows). Values remain bytes; call string(result.value) when UTF-8 is required. No environment setter is introduced; children inherit the parent environment.

A direct command runner

weave "stdlib/process.ramos"
fn main() {
    let arguments = array(string, 1, s"--version")
    let result = process_run(string(arg(1)), arguments)
    if result.status != 0 { stderr("cannot start or wait for process\n")
        exit(1) }
    print(result.code)
}

process_run(executable: string, arguments: [string]) -> ProcessResult waits synchronously and returns code: int64, status: int64. Success has status zero, even when the child exits nonzero. OS failure has negative status and code -1. On Linux, normal exit codes are 0..255 and signal termination maps to 128+signal. Windows returns the unsigned 32-bit process exit code in int64.

Supply an executable path, with .exe on Windows. No PATH search, shell, command-string evaluation, implicit interpreter or batch-file handling is added. The child inherits cwd, environment, stdin/stdout/stderr. Existing redirection and pipes on those standard streams work; output streams are not captured in managed memory. Nonstandard Ramos file/directory handles are not inheritable. Close active TUI/GUI state before running an interactive child. There is no asynchronous spawning, process cancellation, redirection API or timeout yet.

Arguments preserve Unicode, empty values, spaces, tabs, quotes, backslashes and shell characters as values. Embedded NUL returns -22. The limit is 256 argument values, plus argv[0], and 32767 packed UTF-8 bytes; exceeding the public library limit returns -7. On Windows this count includes executable quoting, spaces and escaping, and UTF-16 conversion is also bounded. Quoting follows the Microsoft CRT argument rules and is tested with Ramos and Python children. A Windows child with its own nonstandard parser may interpret its command line differently.

The internal _process_run(executable: bytes, packet: bytes) is an OS boundary, not the library contract. Linux packets are NUL-separated arguments with a final NUL (empty packet means no arguments). Windows packets contain the fully quoted UTF-8 command line including argv[0]. Prefer the typed process_run helper. Linux uses fork/execve/wait4 and a close-on-exec pipe so exec failures cannot be confused with child exit 127. Windows uses explicit lpApplicationName with CreateProcessW, waits, reads the exit code and closes both returned handles.

Native stream API

Paths are bytes, with the existing nonempty/no-NUL/4095-byte contract. Linux accepts host path bytes; Windows validates UTF-8 and converts to UTF-16. Stream IDs are positive opaque generation numbers, not OS descriptors or addresses. At most 64 streams can be open. Closed IDs cannot act on a reused slot.

Intrinsic Signature Result
stdout (bytes) -> int64 Exact bytes, no added newline; zero or negative status
file_open (bytes, int64) -> int64 Positive ID or negative status
file_read (int64, int64) -> bytes Up to requested bytes; check io_error()
file_write (int64, bytes) -> int64 Full-buffer write; zero or negative status
file_eof (int64) -> bool Sticky EOF observed by a positive-size read
file_seek (int64, int64) -> int64 Absolute nonnegative read offset, or negative status
file_close (int64) -> int64 Close once; zero or negative status

Open modes are 0 read-only, 1 create a new write-only file, 2 write-only append (create if missing). Reads/seek/EOF require read mode; writes require write mode. Non-regular files/directories are rejected. Linux opens nonblocking/close-on-exec and validates file type, so a FIFO cannot block. Each read is 0..1 MiB; a file's total size is not capped at 1 MiB. Short reads are allowed. Zero-length reads do not observe EOF. A positive-size zero-byte read sets EOF; a successful seek clears it. EOF is observed by reading, not predicted from a sampled file size.

All stream operations update io_error(), including successful EOF checks. Invalid IDs or wrong modes report -9, invalid counts/offsets/modes -22, and a full registry -24. Other OS failures use negative statuses; Windows retains its common error mapping. Parse status remains independent. Close retires the ID even if the OS reports an error, preventing double-close/reuse mistakes. Applications must close resources; memory collection does not close a stream. The operating system releases remaining handles when the process ends.

Append and write_file replacement reject identities of all active input streams, the last successfully opened/read input and compiler-protected source files. That includes hardlink aliases. Closing an input removes its active-stream protection; most-recent-input protection remains. Creation never truncates an existing file. Callers control the destination directory, as with existing I/O.

Streaming writes are immediate, not atomic transactions. A failed copy may leave a partial new destination; rcopy reports this and exits 1. Existing write_file remains the atomic bounded publisher, with its old flags and failure-preservation contract. read_file keeps its 1 MiB whole-file limit. Linux ignores SIGPIPE so fallible stdout can report -32; existing print/stderr still exit 1 when writing fails. Neither API promises power-loss durability.

fn main() {
    let input = file_open(arg(1), 0)
    if input < 0 { exit(1) }
    var done = false
    while !done {
        let chunk = file_read(input, 65536)
        if io_error() != 0 { file_close(input)
            exit(1) }
        if buffer_len(chunk) == 0 { done = true }
        else { if stdout(chunk) != 0 { file_close(input)
            exit(1) } }
    }
    if file_close(input) != 0 { exit(1) }
}

TUI API and lifecycle

weave "stdlib/tui.ramos"
fn main() {
    if tui_begin() != 0 { stderr("interactive terminal required\n")
        exit(1) }
    tui_color(6, 0)
    tui_box(1, 1, 40, 8)
    tui_at(3, 3, s"Hello from Ramos")
    tui_at(6, 3, s"Press q to quit")
    var done = false
    while !done {
        let key = tui_key(100)
        if io_error() != 0 { tui_end()
            exit(1) }
        if key == 113 || key == 27 || key == 3 { done = true }
    }
    if tui_end() != 0 { exit(1) }
}

tui_begin starts native terminal input and enters an alternate screen, hides the cursor and clears. tui_end resets color/cursor/screen and restores saved native input/output modes; stopping twice succeeds. Additional helpers: tui_write, tui_at(row,column,text), tui_move, tui_color(fg,bg), tui_reset, tui_clear, tui_box(row,column,width,height), tui_safe(bytes,width) and tui_key(timeout_ms). Coordinates are 1-based. Colors 0..7 are black, red, green, yellow, blue, magenta, cyan, white. Text does not add a newline. Callers clip layout to the screen; Unicode scalar length is not terminal display-cell width.

Native primitives are terminal_start/stop() -> int64, terminal_width/height() -> int64, and terminal_key(timeout_ms) -> int64. Start requires both stdin and stdout to be interactive; failure preserves existing modes. Starting twice reports -16. Dimensions report zero with a negative I/O status when unavailable. A key timeout is -1 with status zero; a read failure is -1 with negative status. Timeout is -1 (block) or 0..2147483647 milliseconds. Calling key input without start reports -25.

The first key contract supports ASCII/control keys and navigation. Linux's native primitive returns input bytes; tui_key decodes common VT arrow, Home/End/Page/Delete sequences with a 30 ms escape-sequence grace period. Windows reads native key-down console events and maps navigation directly. Codes: Up 256, Down 257, Right 258, Left 259, Home 260, End 261, PageUp 262, PageDown 263, Delete 264; Escape 27, Enter 13, Ctrl+C 3. Non-ASCII Windows text input is ignored; Linux non-ASCII bytes are not assembled into Unicode keys. Unknown/incomplete escape sequences return Escape and may consume their prefix. Do not mix this input with read_line or another stdin reader.

Normal return, explicit exit and Ramos runtime traps restore the terminal. Linux also restores on SIGHUP/SIGINT/SIGTERM; Windows installs a console control handler that attempts cleanup on OS control termination (tested with Ctrl+Break). Ctrl+C is delivered as a key during raw input, so a custom TUI must handle it (the viewer does). Uncatchable termination such as SIGKILL cannot run cleanup. Applications must be foreground terminal processes. Suspended/background terminal job control is not implemented here.

Linux uses tty ioctls and poll/read syscalls. Windows uses console modes, key events and console control callbacks. There is no curses dependency, delegated renderer, GUI toolkit or runtime host language. TUI means a terminal interface; desktop windows/widgets use the Windows GUI API, added in 0.13.

Coordinates and dimensions are integer client-area pixels. Windows supplies font rendering, focus, Tab navigation, button activation, text selection and editing. Function Behavior
gui_open(title, width, height) -> int64 Open one resizable window; zero succeeds, negative status fails
gui_label(id, x, y, w, h, text) Native text label
gui_button(id, x, y, w, h, text) Native clickable button
gui_input(id, x, y, w, h, text) Single-line editable Unicode text

Every control gets a unique ID 1..64. Creation order determines the native Tab order. There is one top-level window per process; close it before opening another. IDs are local to the current window and can be reused after close; applications must not retain old IDs as references to old windows. Call gui_event regularly: it dispatches OS painting, keyboard and control messages. There are no arbitrary callbacks into Ramos or exposed native handles.

GuiEvent has kind, id, width, height fields:

Kind Meaning Fields
0 Timeout Other fields zero
1 Close requested App should finish its loop and call gui_close
2 Button activated id is the control ID
3 Client resized width, height are current client pixel dimensions
4 Parent window key-down id is a Windows virtual-key code

Text inputs consume normal editing keys themselves; kind 4 is not a global keyboard hook. Colored panels provide basic rectangular drawing. Resize events include the initial layout and minimization (zero dimensions). The Notes example keeps a minimum logical layout of 360x240 and clips when the client is smaller. Clipboard/editing behavior belongs to the native controls.

Limits, statuses and lifetime

Window titles are at most 4095 UTF-8 bytes. Text passed to controls is at most 32767 UTF-8 bytes; edit controls accept at most 32767 UTF-16 units through native editing. Reading can therefore produce more than 32767 UTF-8 bytes. Invalid UTF-8 and embedded NUL are rejected at the native boundary. Strings stay validated; empty labels and edits are allowed. Initial client width is 160..4096 and height 80..4096. Control positions are 0..8192 and dimensions 1..8192; drawing is clipped by the native client area. There are at most 64 controls and 64 queued events. A full queue fails explicitly instead of silently losing user actions.

gui_open and gui_close return fallible statuses. Widget/event helpers call gui_check, so they fail with a diagnostic and exit 1. Low-level _gui_* intrinsics are reserved library machinery; they return negative statuses (or empty bytes with io_error) and validate every property independently: -9 inactive window/unknown control, -16 second active window, -17 duplicate ID, -22 invalid argument/encoding, -27 oversized read, -38 missing platform backend, -75 event queue overflow, and native errors mapped to existing I/O statuses. The old checked arithmetic, allocation and bounds contracts remain.

The reclaiming heap roots the GUI state. Collection does not close native windows. Close releases the controls and owned brushes; the default GUI font is borrowed, and the two system DLLs are process-owned. Normal main return, exit and native Ramos traps attempt GUI cleanup automatically. Process termination also releases OS resources; no durability or user-data save is promised on an abrupt termination. GUI calls run on the program's single main thread.

Runtime and executable format

The Ramos emitter writes PE headers, sections, imports and a relocation directory itself. Code is read/execute, literals are read-only, import slots are read/write, and the value heap is read/write. No section is both writable and executable. The PE advertises NX compatibility and ASLR, uses position-independent code and contains no timestamps or build paths. The imports are Windows' built-in KERNEL32.dll and SHELL32.dll; no compiler tool, CRT or interpreter is imported. GUI startup loads USER32/GDI32 from System32 through LoadLibraryExW; ordinary CLI programs never initialize a GUI. Control creation and rendering use native system calls, and the default console subsystem remains unchanged.

The private Ramos calling convention remains the same. A small native API bridge aligns the stack and reserves Windows shadow space for system calls. Function frames probe each stack page before reserving larger frames, preserving Windows stack guard behavior. Arithmetic, buffer, allocation and call-depth checks remain.

Arguments use Windows' command-line parsing rules and are converted from UTF-16 to UTF-8. Paths are converted from UTF-8 to UTF-16 with invalid encodings rejected. Whole-file read_file rejects non-disk files/directories and enforces the 1 MiB bound; 0.12 streams process regular files in bounded chunks. Atomic write_file writes use a separate same-directory temporary file, handle partial writes, close the file and publish it with MoveFileExW. Existing output requires the replacement flag, and source/hardlink aliases are rejected even with replacement enabled. Temporary files are cleaned up on failure. Windows output paths are made absolute once before publication; unlike the Linux publisher, directory-handle anchoring is not implemented. Both publishers assume the caller controls the destination directory; neither promises crash durability.

platform() returns 0 on Linux and 1 on Windows. All other intrinsic signatures remain unchanged. Windows maps OS errors into common negative statuses: -2 missing file/path, -13 access denied, -17 already exists, -22 invalid path or source alias, -27 oversized/growing input, -36 path too long, and -5 other I/O failures. File-operation status stays fallible. The executable flag to write_file is accepted on Windows; executable format and .exe naming determine how it is launched, rather than POSIX permission bits.

How the compiler builds itself

The compiler implementation is compiler/ramos.ramos. It reads source files, lexes and checks tokens, discovers typed signatures, resolves scoped symbols, emits native x86-64 instructions, resolves labels, writes ELF64 or PE32+ headers, and publishes the resulting executable. It does not interpret Ramos, launch another compiler, or delegate machine-code generation.

Reproduce from a clean checkout

On x86-64 Linux with GNU binutils, Make and Python 3:

make clean all selfhost

The actual compilation chain is:

as --64 -o build/stage0.o bootstrap/src/ramos.s
ld -z noexecstack --build-id=none -o build/stage0 build/stage0.o
./build/stage0 build compiler/ramos.ramos -o build/stage1 --force
./build/stage1 build compiler/ramos.ramos -o build/stage2 --force
./build/stage2 build compiler/ramos.ramos -o build/stage3 --force
cmp build/stage2 build/stage3
sha256sum build/stage2 build/stage3

Stage 0 is the retained assembly compiler seed with the audited native runtime. It supports the compiler source subset; application grammar and new OS intrinsic names are provided by the Ramos-written compiler. Stages 1, 2 and 3 are compiled from the same Ramos compiler source. Stage 1 can differ in instruction selection from stage 2; the required fixed point is stage 2 = stage 3. make all copies stage 2 to the normal ramos executable.

The proof harness additionally runs stage 2 with PATH=/nonexistent, verifies that its output still matches stage 3, and runs the language/I/O corpus (the retained seed skips post-0.7 grammar tests) with stages 0, 2 and 3 (the Linux-only assembly bootstrap skips target selection). It writes hashes and checks to build/bootstrap-proof.json. The GitHub Actions workflow rebuilds this chain and preserves the report and native compiler as artifacts. A local proof snapshot is in bootstrap-proof.json; CI is the reproducible authority.

Implementation boundary

The entire compiler pipeline is Ramos source, including the machine-code and ELF/PE emitters. The private native runtime is represented as a hexadecimal literal inside that source. It provides checked arithmetic diagnostics, integer/boolean/float printing, reclaimed values, string/aggregate operations, and native OS boundaries for arguments and file I/O. The literal is instruction data, not an embedded compiler executable.

The runtime's assembly source remains in bootstrap/src/runtime.inc, buffer_runtime.inc, heap_runtime.inc, values_runtime.inc, io_runtime.inc, text_runtime.inc, stdin_runtime.inc, float_runtime.inc, source_guard.inc, stream_runtime.inc, stream_os.inc and terminal_os.inc. The proof verifies every embedded byte and native entry offset against the bootstrap's emitted runtime. Retaining an assembly OS boundary does not mean the Ramos compiler invokes assembly at run time; once stage 1 is seeded, the next stages require no assembler or linker.

The compiler uses byte buffers as packed token, function, symbol, operator, block and fixup tables. A bounded iterative expression parser and explicit block stack avoid depending on the generated runtime's 64-call limit for deep syntax. The compiler deliberately retains byte-buffer source so the old grammar can seed it. User programs can use the new structs and typed arrays; no preprocessing or host-language parser is required.

The self-hosted compiler has tighter token/output limits than the bootstrap, which are documented in compiler/README.md. Diagnostics preserve filename, line and byte-column formatting and give specific reasons. Native behavior, traps, output preservation, scopes, calls and ELF permissions are covered by the shared corpus.

Limits and standard library reference

The self-hosted compiler accepts up to 64 regular source files totaling 1 MiB (with boundary separators), at most 50,000 tokens including EOF, 4,096 total declarations including parameters and ended blocks and hidden range-bound slots, 256 functions and 16 parameters per function. Structs are limited to 64 types with 16 fields each; array type nesting to 16. Expression and block depth remain bounded at 128; generated programs allow 64 active calls. Its output and decoded string-data arenas are each 1 MiB; labels and fixups each have a 40,000-entry bound. These are checked limits. The retained bootstrap has the older 4 MiB output and IR limits. See compiler representation limits.

The compiler is self-hosted; namespaces, more library types, wrapping arithmetic, broader optimization and additional targets remain future work. Performance claims need new repeatable measurements. The runtime provides checked arithmetic and bounded buffers, but generated programs execute with the caller's operating-system permissions. General canvas graphics, games, a Linux GUI backend and browser support need further platform work.

Tasks and correctness

  • LCG: serial multiply/add/modulo recurrence with runtime seed.
  • Branches: runtime-generated parity and divisibility branches with checksum.
  • GCD: Euclidean remainder loops on varying positive inputs.
  • Recursion: traverse a depth-12 binary tree with runtime-dependent child values and leaf checksum.
  • Byte hash: visit a 4 KiB buffer and update a bounded polynomial hash.
  • Insertion sort: refill and sort 128 bytes; checksum weights sorted positions.
  • Matrix: multiply two 16×16 byte matrices, writing one input cell per pass, reduce output cells modulo 256, then checksum weighted positions.
  • Text scan: classify digits, uppercase ASCII and spaces in 16 KiB; write one byte per pass.

Programs use the same algorithms, sizes, deterministic data and work count in all four languages. Work counts and seeds come from command-line arguments, so answers are not compile-time constants. All 32 task implementations pass independent reference checks at counts 0, 1 and 7 with seeds 1, 17 and 123. Full-size outputs are checked against references on every warmup and timed execution. Native compilers can optimize code normally; recursive calls may be transformed or inlined.

Measurement method

  • 9 timed samples per task/language; randomized language order within each round, sequential execution, two verified warmups.
  • Work counts calibrated until both C and Rust took at least about 30 ms in the calibration probes. The same count is then held fixed for all languages.
  • Work counts are reused from the supplied baseline without recalibration.
  • Pinned to logical CPU 0; Python perf_counter_ns wall clock.
  • Shared virtual machine; CPU frequency, other tenants and background activity are not controlled. Warm filesystem caches; no Windows performance claim.
  • CPython executes source scripts normally, including parsing on every launch. C/Rust/Ramos binaries are built before execution timing.
  • GCC: -O3 -std=c11, with checked add/subtract/multiply builtins and explicit byte bounds.
  • Rust: -C opt-level=3 -C overflow-checks=yes -C panic=abort; safe byte indexing/conversion.
  • Ramos: default native backend (release instruction selection described in the repository); arithmetic, buffer and call-depth checks retained. Python integers stay within signed 64-bit range for these inputs. C/Rust can eliminate provably redundant checks; Python has no Ramos-style call-depth or byte arena limit. Limits are not reached by the suite.

What comes next

Goal: make Ramos a simple native language for useful CLI, TUI and desktop applications on Windows x64 and Linux x64. A beginner should be able to build and run a small tool from a short example; larger tools should have the libraries, diagnostics and resource handling needed to keep working.

This development plan starts from 0.13. The 0.14 syntax, 0.15 OS libraries, 0.16 authoring tools, 0.17 text builders and 0.18 float/math are now implemented; all remaining milestones below are proposals. Proposed version labels below describe order, not deadlines. Keep each release small enough to implement and verify completely; split a milestone if necessary. Python-like ease and Rust/C-like native performance are design aims, not promises of ecosystem parity or benchmark superiority.

The user's rules

1. Simple. Keep a small, readable syntax and one clear way to perform common tasks. Preserve weave for libraries. Put ordinary helpers in Ramos libraries instead of growing the compiler for every convenience. Prefer inferred local types, useful defaults and examples over configuration. Common text, file and GUI operations should not require hand-written byte manipulation.

3. Fast. Keep direct native ELF/PE generation and the self-hosted compiler. Measure speed rather than infer it from native output. Avoid needless copying, allocations and idle polling. Optimize costs observed in real applications; performance claims must identify the release, machine, workload and measurement.

No rule 2 was supplied. Correctness remains a release prerequisite: preserve checked arithmetic, bounds, UTF-8 contracts, resource cleanup and deterministic self-hosting. Any change in those contracts must be explicit and tested.

Starting point

0.13 already has immutable strings, reusable managed memory, structs, typed arrays, weave, a small standard library, streamed files, stdin, CLI/TUI tools and a Windows GUI library. Those foundations should be extended, not rebuilt. The Linux desktop backend is still missing. Live memory, individual values, recursion and source size have documented limits. The published comparative timings are historical; they are not a performance result for 0.13.

0.14: specify the small syntax changes first

Define range bounds as evaluated once, with the upper bound excluded. Specify loop-variable scope, break, continue and checked iteration overflow. Define compound assignment so its destination is evaluated once, including fields and array indices. Retain checked arithmetic and useful errors.

Start with += and -=; do not also add ++ merely to duplicate the same task. Review per-function stack requirements before increasing recursion depth. A larger constant alone does not solve stack safety.

Record a fresh 0.13 performance baseline before compiler changes. Existing programs must still compile, and the simplified example must have matching output. Measure compile time as well as the affected runtime workloads.

0.15: file tools as the first practical application target

Directory iteration must stream entries and release handles when stopped early. Specify Unicode paths, missing files, permission failures and traversal policy, including symbolic links, so recursive tools cannot accidentally loop forever. Use fallible results for expected OS failures, consistent with existing I/O.

Child processes receive an executable and argument values directly. Shell interpretation should require an explicit separate choice. Specify inherited or redirected stdin/stdout/stderr, waiting and exit status. Avoid capturing unbounded output into the managed heap.

Test empty directories, Unicode filenames, large streamed files, failed copies, early exit and child failures on native Windows and Linux.

Performance evidence

Use at least eight workloads spanning integer arithmetic, recursion, arrays, strings, allocation, file streaming, parsing/search and numerical rendering. Compare equivalent C, Rust and Python implementations on the same machine; verify results before timing, record toolchain versions and build flags, repeat runs and report medians and variability. Explain semantic differences, including checked arithmetic. Benchmark input must be large enough to separate useful work from process startup.

For a C-relative execution index, define C as 100 and each Ramos task score as 100 * C_time / Ramos_time; the overall score is the geometric mean of the task scores. Report per-task results and Rust/Python ratios too. A score above 100 means faster on this suite, not a better language. Track startup time, compile time, binary size and peak memory separately from the speed index.

Investigate regressions outside measured variability and explain any deliberate tradeoff. Never reuse old benchmark numbers as evidence for a new release. Documentation-only edits do not require rerunning the performance suite.

Guide for AI coding agents

This chapter is a compact capability contract for agents generating Ramos programs. Target 0.18.0 unless the task explicitly provides a newer compiler and verified documentation. Read the relevant chapter rather than guessing from Python, C or Rust syntax.

Read in this order

  1. Language: statements, types, operators and functions.
  2. Values: immutable strings, aliases, arrays and heap behavior.
  3. Libraries and signatures.
  4. Files, CLI/TUI or GUI for the task.

Supported source patterns

  • One parameterless fn main() returning void per executable; none in libraries.
  • Newline-separated statements and braces; no semicolons.
  • let for an immutable binding, var for a reassignable binding. Inferred local types cannot change. Mutating a field/array/byte value through let is allowed.
  • Function parameters use explicit types; omitted return type is void.
  • if/else if/else, while, for, break, continue, &&, ||, !; boolean conditions. Range bounds are int64, evaluated once and end-exclusive; loop counters are immutable and local to the body.
  • int64, float64, bool, bytes, string, named structs and [T] arrays.
  • "bytes" and s"UTF-8 string" have different types. Conversions copy.
  • weave "relative/path.ramos" is top-level and resolves relative to its file.
  • Use += for matching int64/float64/string values and -= for int64/float64. These are statements, with destinations evaluated once before the RHS. Local bindings must be var; a for counter cannot be reassigned.

Do not invent these features

No import, ++, *=, /=, bitwise/shift operators, exceptions, nullable pointers, generics, methods, closures, namespaces, package manager, asynchronous child spawning, environment mutation or recursive backup. Both else if chains and nested if blocks are supported. Planned features in the roadmap are not current capabilities. Do not substitute Python or C as a hidden backend for Ramos code.

Error and lifetime contracts

Integer overflow, divide-by-zero, invalid bounds and malformed string UTF-8 trap with a diagnostic and exit 1. Expected file failures are fallible instead. Check io_error() immediately after operations that use it; another operation can change it. Check parse_error() after text_to_int or num_parse; zero as a return value alone does not distinguish a successful parse from failure.

arg_count() includes the executable name. Use arg() for bytes, cli_arg() for validated strings. Process the final nonempty stdin line even if EOF is set. Close file streams and directory iterators explicitly; GC reclaims memory, not OS handles. Do not mix buffered stdin reading with raw terminal input.

For directories/processes, read OS contracts. Use directory entry kinds, skip links/junctions during traversal, and close after early exit. process_run(executable: string, arguments: [string]) has explicit status/code; there is no shell or PATH lookup. Supply an executable path; at most 256 argument values and 32767 packed UTF-8 bytes. Child input/output is inherited, not captured. system_env returns bytes and distinguishes missing (-2) from empty success.

For GUI, support is Windows-only. Pump events regularly, use blocking waits when idle and close the window. Do not promise dialogs, canvas APIs or a Linux backend. For TUI, require an interactive terminal and restore it before exit.

For incremental text, use the text builder. Check append status (0 or -27); byte count differs from Unicode scalar count. Snapshot strings are independent; clear reuses capacity and release drops storage for normal collection. Do not access backing fields to bypass UTF-8 checks.

For numerical code, read float64 and math. Use explicit float64(int64) and float_to_int(float64); mixed numeric operations fail. Float overflow/non-finite results, division by zero, invalid conversion and negative nonzero square root trap; gradual underflow is allowed. Printing uses six fractional digits; float_to_text/math_text allow 0..18 fixed digits, not lossless round trips. Do not invent NaN/infinity or text-to-float input APIs.

Build and verify

Use ramos run app.ramos -- ARG... for local native execution; stdin, stdout and stderr are inherited and child exit codes are forwarded. Use build for saved or cross-target executables and --gui. ramos fmt app.ramos --check checks formatting; fmt app.ramos -o copy.ramos writes an atomic copy and protects source aliases. It validates lexical syntax only, not full types. Errors show an escaped source line and caret with byte-column locations. Read authoring contracts before relying on temp-file lifetime.

For a native downloaded compiler on Linux:

./ramos-linux-x86_64 build app.ramos -o app
./app

For Windows:

.\ramos.exe build .\app.ramos -o .\app.exe
.\app.exe

Preserve existing user files; --force intentionally replaces outputs. Compile before reporting working syntax. Check expected output, exit status and failure paths relevant to the app. Cross-compiling proves emission, not native GUI/TUI interaction. Do not claim a speedup without equivalent workloads and timings.

When changing compiler internals, use the main repository's native suites and Linux/Windows fixed-point proofs. This book repository only builds and checks documentation. Its build dependency is not a Ramos runtime dependency.
